# ChairX — ERP/CRM для продажи кресел

ChairX — собственная внутренняя система для небольшого магазина кресел в Кыргызстане. Она объединяет **каталог, закупки, два склада, продажи, доставку, клиентов, возвраты, финансы, закрытие дня и управление сотрудниками**. Интерфейс адаптирован под работу с телефона и компьютера.

> **Статус на 11.10.2026:** описана фактическая кодовая база `main` (`687c93605a5a`), включая UI-улучшения до PR #46 и F12. Это **не подтверждение готовности к production**: перед реальной эксплуатацией остаются проверки из [F13](docs/f13-production-readiness.md). Черновая работа над изолированными demo-fixtures (PR #47) не включена в `main` на момент аудита.

## Что реализовано

| Раздел | Основные возможности |
|---|---|
| Главная | Статистика заказов, доставок и остатков по имеющимся правам; недоступные метрики не раскрываются |
| Продажи | Список и канбан, черновики, подтверждение с резервированием, карточка заказа, отмена/выдача |
| Доставки | Самовывоз, город/регионы, сроки, отправка, вручение, неуспешная доставка и возврат на склад |
| Склады | Остатки HOME/OFFICE, резерв/блокировка, движения, перемещения, управление складами |
| Клиенты | Создание и редактирование, поиск, карточка и история заказов при соответствующих правах |
| Закрытие дня | У сотрудника — личные завершённые продажи и лично собранные CASH/BANK; у руководителя с `FINANCE_READ` — общий отчёт компании с корректировками |
| Каталог товаров | Модели и вариации, SKU, цена, статусы, серверная фильтрация; фотографии не обязательны |
| Закупки | Поставщики, закупки и карго, частичная приёмка на разные склады, платежи поставщикам |
| Возвраты и брак | Частичные возвраты, денежные компенсации, обмены, дефекты и списание |
| Финансы | CASH/BANK, поступления, расходы, CashFlow, внутренние переводы и начальные остатки |
| Администрирование | Сотрудники, активация, пароли, системные/произвольные роли, назначения и журнал безопасности |

## Роли и безопасность

В базе при первоначальной настройке существуют **три системные роли**:

- **ADMIN** — административные и все штатно назначенные бизнес-разрешения.
- **MANAGER** — расширенные операционные права; не имеет права управлять администраторами, возвращать деньги клиентам или выполнять произвольные финансовые переводы.
- **EMPLOYEE** — базовые операции с продажами и клиентами, чтение некоторых данных и закрытие дня; не получает общих прав управления складом и финансами.

Администратор может **сам создавать любые пользовательские роли** (например, «Курьер», «Кладовщик», «Кассир») и выбирать для них разрешения; эти роли **не создаются автоматически**. Один пользователь может иметь несколько ролей, а права объединяются. Отдельный технический логин `catalog` не является сотрудником.

**Полная поимённая матрица всех 61 разрешения, назначенных ADMIN/MANAGER/EMPLOYEE, и управление ролями:** [Роли и права](docs/roles-and-permissions.md). Реальные права существующей БД могут отличаться от миграционного значения после административного редактирования ролей.

Безопасность обеспечивается сервером (Spring Security, HTTP Basic, CSRF, deny-by-default). Скрытие кнопок в React **не заменяет** проверки на API. Дополнительно: [Security/RBAC](docs/security-rbac.md), [F12](docs/f12-administration.md).

## Важное ограничение: закрытие дня

**Разделение исправлено в ветке персонального закрытия:** сотрудник с `DAILY_CLOSING_READ` видит только собственные завершённые продажи и оформленные им поступления; POST фиксирует отдельный персональный snapshot. Общие CASH/BANK доступны только при `FINANCE_READ`, операции закрытия компании требуют дополнительных прав. Личный snapshot не переводит деньги и не заменяет общий бухгалтерский отчёт. См. [личное закрытие](docs/employee-daily-closing.md) и [аудит](docs/audit/2026-10-11-documentation-audit.md).

## Технологии

- **Backend:** Java 25, Spring Boot 4.1.1, Maven, Spring Security, Spring JDBC/JdbcClient, Flyway.
- **Frontend:** React 19, TypeScript, Vite 8, React Router, TanStack Query, Tailwind CSS.
- **Данные:** PostgreSQL 17; миграции Flyway **V1–V52**, денежная единица — **сом (KGS)**; расчётный день — **Asia/Bishkek**.
- **Среда:** Docker Compose (PostgreSQL + backend + frontend), Testcontainers для backend интеграционных тестов.

Архитектура, таблицы, транзакции, REST, тесты и эксплуатация: [Технический справочник](docs/technical-reference.md).

## Локальный запуск

Нужен Docker Desktop/Engine с Compose и `openssl`. Выполнять из корня репозитория:

```bash
bash scripts/init-local-env.sh
docker compose up -d --build --wait
docker compose ps
```

UI: **http://localhost:5173** · API: **http://localhost:8080** · PostgreSQL: **127.0.0.1:5432**. Vite проксирует запросы `/api` в backend.

Для повторного запуска: `docker compose up -d`; для отслеживания изменений: `docker compose up --watch`. Для остановки без удаления данных: `docker compose down`. **Не используйте `docker compose down -v` на базе с нужными данными.**

Локальный профиль автоматически создаёт логины `admin`, `manager`, `employee`; их начальные пароли записаны в **локальный** `.env` (`CHAIRX_BOOTSTRAP_ADMIN_PASSWORD`, `CHAIRX_DEV_MANAGER_PASSWORD`, `CHAIRX_DEV_EMPLOYEE_PASSWORD`). Пароли в БД хешируются и **не пересоздаются при каждом запуске**. Логин `catalog` — только технический доступ к каталогу. В `.env.example` есть пример пароля БД, он **не пригоден для production**. Не публикуйте `.env` и не копируйте пароли во frontend/`VITE_*`.

Подробности: [Локальная разработка](docs/local-development.md).

## Проверки

```bash
cd backend && ./mvnw clean verify
cd ../frontend && npm ci && npm run lint && npm run typecheck && npm test && npm run build
```

Backend integration использует отдельную тестовую PostgreSQL `chairx_test` через Testcontainers; для тестов нужен работающий Docker. В `.github/workflows/` есть backend/frontend проверки, Docker smoke и приёмочные сценарии F11. Успешный CI **не подтверждает** физическую сверку склада/кассы и безопасный запуск в интернете.

### Документация как часть изменений

При новом API: обновить endpoint-матрицу и негативные RBAC-тесты. При изменении прав: обновить SQL/Flyway, [матрицу](docs/roles-and-permissions.md) и тесты. При изменении UI: обновить [разделы](docs/system-features.md) и доступность маршрутов. Старые документы P17/P20/F01 имеют исторические статусы и не должны использоваться как текущий release report.
