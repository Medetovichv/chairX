# ChairX — отдельное личное закрытие дня сотрудника

**Статус:** реализовано и объединено с `main` в [PR #51](https://github.com/Medetovichv/chairX/pull/51), merge commit [`5aded096`](https://github.com/Medetovichv/chairX/commit/5aded0960f68de41f12eae1f614d55678881646b) (11.10.2026). Исправлена прежняя доступность общего CASH/BANK сотруднику, но эта функция не является заменой общего бухгалтерского отчёта.

## Безопасность и разграничение

- `/api/finance/closings/**` — **общие** бухгалтерские отчёты компании: нужен `FINANCE_READ` для чтения и **дополнительное** соответствующее разрешение на изменение. Сотрудник, имеющий только `DAILY_CLOSING_READ`/`WRITE`, не видит общие суммы даже при прямом GET.
- `GET /api/finance/my-closings`, `GET /api/finance/my-closings/{date}`, `POST /api/finance/my-closings/{date}` — **личная** оперативная сверка сотрудника. Read требует `DAILY_CLOSING_READ`, write требует `DAILY_CLOSING_WRITE`. Identity берётся строго из HTTP Basic authenticated principal и активного `app_users`. Параметр `userId` не поддерживается.
- `sales.created_by` определяет автора продажи, но учитываются **только завершённые** продажи за выбранную дату в зоне `Asia/Bishkek` (`SELF_PICKUP.FULFILLED` и доставленный `DELIVERED`).
- Собранные средства вычисляются по **реальным финансовым проводкам** `finance_movements` с `movement_type='SALE_PAYMENT'`, `source_type='PAYMENT'`, `created_by=currentUsername` и `business_date=date`. CASH и BANK здесь — суммы лично оформленных поступлений, **не** компания-wide balance и не задолженность по продажам. Возвраты, отмены и переводы менеджера сохраняются в общем финансовом учёте и в данном «собрано лично» не вычитаются.
- POST отправляет обе ожидаемые суммы с GET плюс фактические суммы и пояснения к расхождениям; backend пересчитывает под `CompletionGuard` и блокировками финансовых счетов в порядке BANK→CASH. Изменение ожидаемых сумм отменяет сохранение с HTTP 409; UI не повторяет POST автоматически.
- Каждая `employee_id + business_date` имеет **один** неизменяемый личный отчёт и снимок только своих завершённых продаж; повторное закрытие возвращает 409. Состояние сохраняется в новых таблицах `employee_daily_closings`, `employee_daily_closing_sales` (Flyway V53). Общие `finance_daily_closings`, `finance_accounts`, `finance_movements`, FIFO и все старые миграции не изменяются. Сохранение личного отчёта записывает только audit.
- После закрытия поступления в текущем company journal могут появиться позднее; GET **не переписывает** личный snapshot, а выставляет `collectionsChangedAfterClose=true` для сверки руководителем.
- Временное окно обычного личного закрытия: сегодня или вчера до 13:00 по Бишкеку; персональный report не получает менеджерскую разблокировку задним числом.
- Frontend выбирает корпоративный экран только при наличии `FINANCE_READ`. Всем остальным с `DAILY_CLOSING_READ` доступен только личный экран, без предварительного обращения к защищённым корпоративным API.

## Границы

Речь идёт только об изоляции **экрана закрытия** и связанных API. Общий `SALES_READ` по-прежнему может открывать список продаж компании через `/api/sales`: введение приватности на всех экранах и отчётах — отдельная полномасштабная политика. Личный отчёт — **сверка и snapshot**, не самостоятельная касса для хранения денег и не закрытие банковского дня компании.

## Тесты

`EmployeeDailyClosingIsolationTest` создаёт двух реальных сотрудников в PostgreSQL Testcontainers, проверяет непересечение их поступлений/продаж и запрет глобальных closing GET/POST; повторный POST, CSRF, технический catalog, неизменность `finance_accounts` и `finance_movements`, позднее поступление после snapshot. Проверено для PR #51: backend 689 тестов (0 failures/errors, 1 skipped), frontend 386/386 тестов, Docker Compose smoke и F11 release gate; [GitHub Actions](https://github.com/Medetovichv/chairX/actions/runs/38159413176). Это не заменяет реальный приёмочный учёт наличных.

Разрешения из V29–V52 **не удаляются** из существующих ролей; принудительный server-level `FINANCE_READ` отделяет корпоративные API от personal-view. При выдаче `FINANCE_READ` кастомной роли этот пользователь получает право читать общий финансовый отчёт согласно общей политике; подобные назначения требует ревью администратора.
