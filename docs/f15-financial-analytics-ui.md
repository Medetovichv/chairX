# F15 — финансовая аналитика (UI, стадия проверки)

Используется существующий финансовый backend из PR #90, frontend из PR #91.
Итоговое ТЗ — прикреплённый документ «CHAIRX F15 — FINANCIAL ANALYTICS»;
HTML-прототип — дизайн-ориентир, не источник финансовых данных.

## Текущие маршруты

| Путь | Назначение | Доступ |
|---|---|---|
| `/finance` | обзор, финансовые счета, KPI, последняя проводка, склад и долг | `FINANCE_READ` для защищённых показателей |
| `/finance/report` | P&L, FIFO, возвраты, начисления, денежные KPI | `FINANCE_READ` |
| `/finance/operations` | серверный журнал, выбор счёта/типа, пагинация, CSV, мобильные карточки | `FINANCE_READ` |
| `/finance/cash-flow` | реальное движение денег | `FINANCE_READ` |
| `/finance/expenses` | расходы и начисления F14, существующие CRUD-действия | `EXPENSES_READ` / `EXPENSES_CREATE` |
| `/finance/obligations` | сумма задолженности и авансов, поставщик, закупка, FIFO остатки сейчас | `FINANCE_READ`; ссылка на документ — `PURCHASE_READ` |
| `/finance/analytics` | помесячная динамика, категории расходов и сравнение чистой выручки/денежного потока с предыдущим календарным годом | `FINANCE_READ` |

Существующие `/finance/transfers` и `/finance/opening-balances` сохранены.

## Источник финансовых показателей

Все суммы в KGS, расчёты денежных величин выполняются в backend (`BigDecimal`).
`/api/finance/profitability` возвращает признанную выручку, FIFO, возвраты, F14
и операционную прибыль; `netProfitAvailable=false` означает, что прибыль показывать нельзя.
Показатели `/api/finance/cash-flow` — поступления и выплаты, **не прибыль**.
`/api/finance/inventory-valuation` и `/api/finance/purchase-obligations`
показывают **текущее состояние**, а не исторический остаток на дату отчёта.

Журнал `/api/finance/ledger` формируется по фактическим проводкам. Его CSV
`/api/finance/ledger/export` использует одинаковые серверные фильтры даты,
счёта и типа движения, права `FINANCE_READ`, UTF-8 BOM и CSV quoting.
Выгрузка свыше 10 000 строк должна быть разбита на меньшие периоды.

## Не считать завершённым без проверки

- Визуальное сравнение с HTML-прототипом и полноценный мобильный QA на 320/360/375/390/430/768 px.
- Переходы: SALE/PURCHASE используют `documentKind/documentId` с проверкой прав. Для EXPENSE/TRANSFER/CUSTOMER_REFUND доступна только ссылка на соответствующий раздел при наличии разрешения; это **не** прямая ссылка на первичный документ. `sourceType/sourceId` пока недостаточны для универсального безопасного навигационного разрешения.
- Единый поиск по номеру документа, тексту, сотруднику и сумме требует серверных фильтров
  с проверкой прав доступа; не подменять его фильтрацией текущей страницы браузером.
- Экспорт крупных выборок должен проходить нагрузочные проверки, а не только функциональные тесты.
- FIFO-оборачиваемость теперь рассчитывается на сервере по неизменяемому журналу `inventory_cost_movements` и времени `stock_movements.occurred_at`: чистое списание себестоимости SALE_OUT минус восстановленная себестоимость RETURN_IN, делённое на среднее из FIFO-остатков на начало и конец. При нулевом или некорректном среднем остатке коэффициент не выдаётся. Требуется проверка на наборах с историческими корректировками и возвратами.
- Категорийная аналитика расходов реализована по текущим начислениям и прямым расходам. Сравнение календарных лет (выручка и чистый денежный поток) использует одинаковые завершённые месяцы для текущего года и полного предыдущего года; для выбора исторического года сравниваются все 12 месяцев. Текущий незавершённый месяц исключён. Сравнение сопоставимых периодов и новое API оборачиваемости требуют итоговой проверки приёмки на реальных финансовых сценариях.
- Приход/расход в P&L и фактические финансовые проводки никогда не объединяются
  в один показатель без явно указанной экономической классификации.

До подтверждения всех согласованных критериев PR остаётся draft.
