# ChairX — разделы интерфейса и бизнес-процессы

**Сверено с `frontend/src/app/router/AppRouter.tsx`, `frontend/src/shared/lib/navigation.ts`, компонентами `frontend/src/features/`, backend controllers и `SecurityConfig` из `main` 11.10.2026.** Навигация отражает функциональность, доступную при наличии соответствующих permission, а не безусловный доступ каждого сотрудника.

## 1. Меню и назначение разделов

Главное меню разделено на группы **Обзор → Ежедневная работа → Управление → Система**. Для верхнего пункта React обычно использует условие «**хотя бы одно** из перечисленных прав». Это **не** означает автоматического разрешения всех действий внутри: каждый запрос имеет свою проверку в backend.

## 2. Основные процессы: от товара до денег

### Каталог → закупка → поступление

1. Создать модель (`products`) и её вариации (`product_variants`): названия, SKU, продажная цена, активность. Фото не является обязательным процессом.
2. Завести поставщика; создать закупку `DRAFT` с несколькими позициями, количеством и закупочными ценами; при необходимости указать карго.
3. Подтвердить `CONFIRMED`. Одна закупка может поступать **по частям** в HOME и OFFICE, не превышая заказанного количества: `PARTIALLY_RECEIVED` → `RECEIVED`.
4. Приёмка создаёт реальные остатки и FIFO-слои себестоимости; распределённая стоимость карго учитывается в стоимости товара.
5. Платежи `SUPPLIER` и `CARGO` возможны частями (при достаточном CASH/BANK) и **не меняют** складские остатки. Повтор запроса с тем же idempotency key не создаёт второй платёж.

### Продажа → склад → выдача или доставка

1. Продажа может начинаться как `DRAFT`: пока не подтверждена, она не резервирует товары и не формирует финансовые проводки.
2. Подтверждение проверяет доступный товар и **резервирует конкретное количество в конкретных складах**, учитывая `available = onHand - reserved - blocked`. Недостаток количества отклоняет операцию целиком.
3. `SELF_PICKUP`: выдача переводит продажу в `FULFILLED` и списывает резерв/FIFO. `CITY_DELIVERY`/`REGION_DELIVERY`: доставка проходит `READY` → `IN_TRANSIT` → `DELIVERED` или `FAILED`.
4. Неуспешная доставка **сама не возвращает товар на склад**: требуется явный `return-to-warehouse` с однократным восстановлением.
5. Платёж продажи в `CASH` или `TRANSFER` (`BANK_TRANSFER`, `MBANK`, `BANK_INSTALLMENT`) формирует финансовую проводку только по факту поступления денег; банковская рассрочка сама по себе не является учётом рассроченного долга.
6. Канбан и карточка отражают **серверные** статусы. Перенос карточки в UI не должен обходить ограничения backend.

### Возвраты, обмены, компенсации, брак

- Частичный возврат ограничен ранее проданным/уже возвращённым количеством и состоянием (`SELLABLE` / `BLOCKED`).
- Обычный клиентский возврат доставки возможен после подтверждённого `DELIVERED`; `FAILED` обрабатывается **отдельным** возвратом в склад из доставки.
- `REFUNDS_CREATE` — реальный возврат денег, не то же самое, что физическое возвращение кресла.
- Обмен связывает исходные и новые позиции; разница в цене урегулируется отдельно (`EXCHANGES_SETTLE`), без двойных проводок.
- Дефект: `OPEN` → `WAITING_PARTS` → `RESOLVED` или `WRITTEN_OFF`. Открытый дефект блокирует доступность товара, списание отражает стоимость.

### Финансы → закрытие дня

- Денежные счета `CASH` и `BANK` ведутся через журнал `finance_movements`; выплаты, поступления, расходы и внутренние переводы имеют разные типы событий.
- Закрытие дня использует дату **Asia/Bishkek**. **Личный** backend возвращает только поступления, зарегистрированные вошедшим сотрудником, и его завершённые продажи; вводятся фактически собранные суммы CASH/BANK и причины расхождений. **Общий** backend рассчитывает ожидаемые остатки компании, доступные по `FINANCE_READ`.
- Закрытие **не создаёт вымышленную денежную проводку**, а сохраняет отчёт с историческим snapshot завершённых продаж.
- Исправления отчётов, временная разблокировка и поздний **реальный** расход осуществляются отдельными API, правами и транзакциями; история и оригинальные ожидания сохраняются.
- **Разделение отчётов:** персональная смена (новые `/api/finance/my-closings/**`) сохраняется отдельно от общего P21 финансового закрытия. Личный отчёт не меняет счета CASH/BANK компании; общая касса доступна только обладателям `FINANCE_READ`. Сверка сотрудников по физическим деньгам и общий бухгалтерский отчёт остаются разными процессами.

## 3. Статусы и справочники

| Объект | Состояния в backend |
|---|---|
| Закупка | `DRAFT`, `CONFIRMED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `CANCELLED` |
| Продажа | `DRAFT`, `CONFIRMED`, `FULFILLED`, `CANCELLED` |
| Доставка | `READY`, `IN_TRANSIT`, `DELIVERED`, `FAILED`, `CANCELLED` |
| Тип исполнения | `SELF_PICKUP`, `CITY_DELIVERY`, `REGION_DELIVERY` |
| Брак | `OPEN`, `WAITING_PARTS`, `RESOLVED`, `WRITTEN_OFF` |
| Обмен | `PENDING_SETTLEMENT`, `COMPLETED` |
| Платёж | `PAID`, `CANCELLED` |
| Возвращённый товар | `SELLABLE`, `BLOCKED` |

## 4. Что эта документация НЕ утверждает

Наличие backend REST endpoint не гарантирует готовность соответствующего процесса к повседневному использованию без дополнительного обучения или UAT. CI проверяет определённые API/браузерные сценарии, но не заменяет ручную сверку кассы и инвентаризацию. Отдельное исследование F13 помечает deployment как **NO-GO** до выполнения его условий. Интеграции WhatsApp/Instagram и полноценные лиды/мессенджеры **не подтверждены как реализованные**. Новое личное закрытие сотрудника описано в [отдельном документе](employee-daily-closing.md); всеобъемлющей приватности `/api/sales` оно само по себе не вводит.
