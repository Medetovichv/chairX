# ChairX — роли и разрешения (актуальная модель RBAC)

**Дата сверки:** 11.10.2026 · **источник:** `main` `687c93605a5abf52be53ce15c5eda00a042268c7`. Эта матрица получена из **реальных Flyway seed/grant migrations V29, V30, V33, V40, V42, V46, V51, V52**, а не из названий пунктов меню. Приведены **61 permission из `security_permissions`** и штатные назначения трём системным ролям **для новой БД после всех миграций**. В существующей базе администратор мог изменить MANAGER/EMPLOYEE, добавить роли и назначения; используйте SQL-проверку ниже.

## 1. Как принимается решение о доступе

1. `app_users` хранит сотрудника, хеш пароля и `active`.
2. `security_user_roles` допускает **несколько ролей** одного сотрудника.
3. `security_role_permissions` связывает роли с конкретными кодами прав.
4. При HTTP Basic права сотрудника берутся из БД; эффективный набор — **объединение** permission всех его ролей. Он отображается в `GET /api/auth/me`.
5. `SecurityConfig` проверяет HTTP method + URL + authority и для администрации дополнительно **действующую системную ADMIN**. Неизвестные API/method получают `denyAll`.
6. В React разрешения применяются к навигации и действиям, но **сервер решает окончательно**. Для операций действуют дополнительные инварианты: остатки, статусы, даты, CSRF, лимиты и т. д.

Наличие разрешения **не означает**, что любой экран откроется без остальных необходимых прав: страница может запрашивать несколько API, а запись может требовать полномочий сверх чтения.

## 2. Системные и пользовательские роли

| Роль | Создание | Назначение и особенности |
|---|---|---|
| `ADMIN` | Системная, UUID `…0001` | Штатно все 61 permission; административные API требуют именно active **system ADMIN**, не просто грант `USERS_*` |
| `MANAGER` | Системная, UUID `…0002` | Операционная работа, просмотр `FINANCE_READ`, управления логистикой/закупками; без системного администрирования или самостоятельных денежных возвратов |
| `EMPLOYEE` | Системная, UUID `…0003` | Базовые продажи, клиенты, чтение каталога/склада/доставок и разрешения дневного закрытия |
| Пользовательская роль | Создаёт ADMIN через `POST /api/admin/roles` | Любой **допустимый** уникальный код, произвольное имя и выбранные разрешения; не наследует ничего автоматически |
| `catalog` | Техническая учётная запись, **не роль БД** | Отдельный HTTP Basic principal с `CATALOG_ACCESS`: только чтение продуктов и вариантов, без сотрудников и бизнес-данных |

Названия «Кладовщик», «Кассир», «Курьер», «Бухгалтер» **не являются встроенными ролями**. Их создают вручную; до назначения конкретных permission они ничего не дают. ADMIN нельзя редактировать; роли MANAGER и EMPLOYEE могут редактироваться администратором в предусмотренных сервером границах.

## 3. Полная матрица разрешений

Условные обозначения: ✅ — грант штатно выдан миграциями; — — не выдан. У ADMIN на новой мигрированной БД все 61 права, в том числе `DAILY_CLOSING_UNLOCK_MANAGER` (V46). Отдельный `CATALOG_ACCESS` **не является** строкой таблицы `security_permissions`.

## 4. Специальные ограничения, которые нельзя понять по таблице

- **Администрирование**: для `/api/admin/**` требуется **active system ADMIN** + соответствующее `USERS_*` / `ROLES_*`; копирование кода роли или прав в custom role этого не заменит. Сервис после блокировки повторно проверяет полномочия. Запрещено оставить систему без последнего активного ADMIN.
- **Создание роли**: `[A-Z][A-Z0-9_]{2,99}`, нельзя коды `ADMIN`, `MANAGER`, `EMPLOYEE`. На custom и при редактировании не-ADMIN нельзя выдавать `ADMIN_ACCESS`, `USERS_*`, `ROLES_*`, `DAILY_CLOSING_UNLOCK_ADMIN`; `CATALOG_ACCESS` не выдаётся никакой обычной роли. `expectedVersion` + `reason` обязательны для обновления роли; устаревшая версия — HTTP 409.
- **Сотрудники**: создать, активировать, деактивировать, изменить назначение отдельной роли, сбросить пароль 12–128 символов. Создание аккаунта и назначение ролей — **две операции**. Активизация сохраняет UUID/назначения. Права `USERS_UPDATE` существуют исторически, но **отдельного PUT/PATCH API редактирования произвольных реквизитов сотрудника на данный момент нет**.
- **Денежные действия**: `PAYMENTS_CREATE` добавляет поступление продажи; `PAYMENTS_CANCEL` отменяет платеж; `REFUNDS_CREATE` возвращает деньги клиенту; `PURCHASE_PAYMENTS_CREATE` платит поставщику/карго; `FINANCE_TRANSFER` переводит CASH↔BANK; `FINANCE_INITIALIZE` задаёт начальный баланс. Это независимые права.
- **Закрытие дня**: личный `GET /api/finance/my-closings/**` требует `DAILY_CLOSING_READ`, личный POST — `DAILY_CLOSING_WRITE`. **Общий** `GET /api/finance/closings/**` требует `FINANCE_READ`, а общий POST/PUT — **одновременно FINANCE_READ** и соответствующее право записи. Разблокировка, поздний расход и аудит общего отчёта требуют дополнительного разрешения **и FINANCE_READ**. Штатный MANAGER получает только `DAILY_CLOSING_UNLOCK_MANAGER`, ADMIN — оба unlock права; `DAILY_CLOSING_UNLOCK_ADMIN` другим ролям не передаётся.
- **Склад**: `INVENTORY_READ` не означает `INVENTORY_TRANSFER` или `INVENTORY_RECEIVE`. Технические DTO inventory transfer не возвращают FIFO `totalCost` даже с правом складского чтения; внутренние стоимостные слои сохраняются в БД. Установление/изменение справочника складов требует `WAREHOUSES_MANAGE`.
- **Каталог**: `CATALOG_READ` и `CATALOG_MANAGE` различны. Технический `catalog` имеет только `CATALOG_ACCESS`, и этот principal **не ADMIN**.
- **Составные запросы**: `GET /api/customers/overview` и `GET /api/sales/customer/{id}` требуют одновременно `CUSTOMERS_READ` **и** `SALES_READ`. Главный dashboard отдаёт лишь разрешённые метрики (отсутствующее поле — `null`, не фиктивный ноль).
- **Интерфейс и сервер**: для `/inventory/warehouses` UI требует два права (`INVENTORY_READ` + `WAREHOUSES_MANAGE`); для `/deliveries/new` — `DELIVERIES_READ` + `DELIVERIES_MANAGE`. Меню верхнего уровня иногда появляется по **любому одному** праву из перечня, но дочерние API защищаются отдельно.

### Личное и общее закрытие — разные API

`/api/finance/my-closings/**` показывает только собственные продажи (`sales.created_by`) и оформленные этим сотрудником поступления из `finance_movements`; identity берётся из HTTP Basic. `FINANCE_READ` требуется сервером для **общего** `/api/finance/closings/**`, в том числе для preview, истории и завершённых продаж. Личное закрытие записывает отдельные снимки V53, не меняет реальную бухгалтерскую кассу и не даёт права отменять чужие платежи. [Полный протокол](employee-daily-closing.md).

## 5. Актуальная проверка прав в работающей БД (read-only SQL)

```sql
-- Фактически назначенные гранты для каждой системной/пользовательской роли.
SELECT r.code AS role_code, r.name, r.system_role,
       r.version, p.code AS permission_code, p.description
FROM security_roles r
LEFT JOIN security_role_permissions rp ON rp.role_id = r.id
LEFT JOIN security_permissions p ON p.code = rp.permission_code
ORDER BY r.code, p.code;

-- Активные пользователи и ВСЕ их роли (не выводить пароль/хеш).
SELECT u.username, u.active, r.code AS role_code
FROM app_users u
LEFT JOIN security_user_roles ur ON ur.user_id = u.id
LEFT JOIN security_roles r ON r.id = ur.role_id
ORDER BY u.username, r.code;
```

Не считайте эту seed-матрицу снимком реальной базы: у системы есть динамические роли. При изменении ролей обновляйте данный документ с указанием `main` SHA и миграции, если меняется **базовый** набор.
