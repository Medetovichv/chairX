# ADR 0001: Foundation и каталог товаров

Статус: реализовано в рамках первого согласованного slice, ожидает проверки владельцем.

## Контекст

Baseline содержит только Spring Boot 4.1.1 на Java 25. На текущем этапе нужны Product и ProductVariant; остальные бизнес-модули и frontend не входят в scope.

## Решение

Один Maven-модуль, один backend и PostgreSQL. Корневой Java-пакет — `kg.chairx`.

```text
kg.chairx
├── ChairxApplication
├── config/SecurityConfig
├── common/web/           ошибки REST и выдача CSRF-токена
├── audit/AuditService    запись аудита в транзакции вызывающего сервиса
└── product/
    ├── api/             отдельные DTO входа, ответа и страниц
    ├── web/             два тонких REST-контроллера
    ├── application/     ProductService, ProductVariantService, mapper, ошибки
    ├── domain/          две JPA-сущности с простыми действиями
    └── persistence/     два Spring Data repository
```

Публичная прикладная граница Product — методы ProductService / ProductVariantService и DTO в `api`. Другие будущие модули не должны обращаться к repositories или менять JPA entities напрямую. Отдельные interfaces без второго implementation не вводятся.

Сервисы определяют транзакции. Чтение возвращает DTO внутри read-only транзакции. Изменения принудительно flush перед формированием ответа и аудита, чтобы включить актуальный updatedAt и выявить ограничения/конфликт версии. Аудит через JdbcClient участвует в той же JPA-транзакции; это проверяется rollback-тестом.

Аудит — минимальная необходимая поддержка административных изменений каталога и цены. Он не является event bus, механизмом восстановления состояния или будущим универсальным журналом бухгалтерии. API редактирования/удаления аудита нет. Полиморфная ссылка entity_type/entity_id намеренно не имеет FK на конкретную таблицу.

Две сущности не требуют BaseEntity. Небольшая повторяемость UUID/timestamps предпочтительнее общей иерархии. optimistic version защищает только пересекающиеся операции; обязательные клиентские версии пока не входят в REST contract.

Категория представлена nullable строкой. SKU не уникален. Изображения отсутствуют до согласования file storage. Цена NUMERIC(19,2) соответствует текущему контракту API; операции финансового распределения и округления ещё не реализуются.

Пагинация обязательна, порядок по UUID детерминированный. PK обслуживает список товаров, индекс `(product_id, id)` — список вариантов конкретного товара. Другие индексы пока не нужны.

Spring Security оставлена активной: один конфигурируемый технический пользователь, обязательный пароль окружения, HTTP Basic, CSRF, единые JSON-ошибки 401/403. CSRF нужен и с Basic, поскольку браузер может автоматически отправлять credentials. Это foundation, а не роли сотрудников. Источники решения: https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html .

Тесты используют управляемый Spring Boot Testcontainers PostgreSQL 17 через ServiceConnection. Тестовый datasource намеренно содержит недоступный запасной URL: без контейнерной конфигурации тест не сможет попасть в рабочую БД. Docker обязателен; fallback на H2 и пропуска тестов нет.

## Последствия и ограничения

Нет межмодульных orchestration-классов: пока отсутствуют процессы, которым они нужны. Нет склада, продаж, закупок, CRM и frontend. Модель сотрудников и granular permissions остаётся отдельным будущим этапом. До добавления финансовых операций нужно согласовать решения Master Specification; каталог их не предрешает.
