# F10 — Finance, Customer Payments, Refunds & Cash Management

**Scope:** React/TypeScript frontend using existing Spring Boot/PostgreSQL financial backend contracts. Branch `feat/frontend-f10-finance`, based on main after F09. No backend/Flyway changes, F01–F09 not rewritten. No manual database ledger or profit calculations.

## Operator workflows
- `/finance`: FINANCE_READ; GET /api/finance/accounts (array of CASH, BANK, balance and initialized); GET /api/finance/cash-flow with current **Asia/Bishkek** month [from,to). Shows incoming, outgoing and net movement, not profit.
- `/finance/cash-flow`: FINANCE_READ; GET /api/finance/cash-flow?from=YYYY-MM-DD&to=YYYY-MM-DD. All ten actual server fields: payments, paymentCorrections, refunds, exchangePayments, exchangeRefunds, operatingExpenses, purchasePayments, totalIn, totalOut, netCashFlow. Period up to 93 days in UI, **to exclusive**. Account-to-account transfers are internal and not external cash flow.
- `/finance/expenses`: EXPENSES_READ list GET /api/expenses?from&to (plain array, no fake page/size/total) and real GET /api/expenses/total?from&to; EXPENSES_CREATE posts `{idempotencyKey,category,amount,paymentMethod,expenseDate,comment}`. Categories ADVERTISING/RENT/SALARY/DELIVERY/UTILITIES/OTHER, paymentMethod CASH/BANK. Positive integer soms; expense date is LocalDate in Bishkek, default current business day, never silently shifted after failure. Closed periods cannot be bypassed using F11 correction API. Create-only expense operator can access creation form without FINANCE_READ or EXPENSES_READ, without fetching protected data.
- `/finance/transfers`: FINANCE_TRANSFER; POST /api/finance/transfers with `transferId`, `from`, `to`, whole-som `amount`. Separate account types CASH/BANK and explicit confirmation; same-account transfer disallowed. Optional FINANCE_READ-gated balance check (backend authoritative); after success refresh both account balances. No global GET transfer/by-ID exists, so unknown outcome requires manual reconciliation or *exact same transferId/payload* retry within original tab, never a new transfer ID.
- `/finance/opening-balances`: FINANCE_INITIALIZE; POST /api/finance/opening-balances with `account` and zero-or-positive whole-som `amount`; explicit one-time acknowledgment. When FINANCE_READ is available read existing initialized state, block if initialized, and cautiously reconcile unknown outcomes by account GET; without read authority rely on backend single-use check and manual verification. Cannot overwrite historical balances.
- `/sales/:saleId`: existing F07 card integrates PAYMENTS_READ history `GET /api/payments/sale/{saleId}`, active `GET /api/payments/sale/{saleId}/active` (404 means none), PAYMENTS_CREATE `POST /api/payments`. **No GET /api/payments**. CreateRequest is `{saleId,method,channel,reference,comment}` — **no amount**, full server Sale.total is posted. CASH→method CASH + account CASH; BANK_TRANSFER / MBANK / BANK_INSTALLMENT→method TRANSFER + account BANK. Bank-installment only after actual money received. Confirm displays sale, customer, total, channel, account. Backend checks CONFIRMED/FULFILLED status, duplicate active payment, returned failed deliveries and Exchange-generated new Sale (must use settlement). UI doesn't claim normal payment safe for Exchange Sale based on absent backend indication; backend forbids it. Cancellation PAYMENTS_CANCEL uses `POST /api/payments/{id}/cancel` with mandatory reason <=1000. Backend reverses the payment and rejects cancellation after any refunds/exchanges; cancel is NOT cancel Sale.
- `/sales/:saleId` (linked from `/returns/:returnId`): REFUNDS_READ `GET /api/refunds/sale/{saleId}`, REFUNDS_CREATE `POST /api/refunds`, exact `{idempotencyKey,saleId,returnId|null,amount,method,reason,reference,comment}`. Positive **integer** som, method CASH/TRANSFER, reason 1–500, reference <=200, comment <=1000. Prefills matching known Return UUID from the link; backend checks ownership, active payment, original sale-line values, previous refunds, Exchange participation and financial account. No second RETURN_IN or frontend stock changes. Do **not** claim a safe max if backend doesn't provide it. No GET global refunds list exists.
- `/returns/exchanges/:exchangeId`: EXCHANGES_READ for GET Exchange and settlements; EXCHANGES_SETTLE for POST `/api/exchanges/{id}/settlements` `{idempotencyKey,direction:IN|OUT,method:CASH|TRANSFER,amount,reference}`. UI derives directional obligation from **backend ExchangeResponse**, subtracts only server-confirmed settlements for advisory remaining and never overrides backend Exchange status. IN credits CASH/BANK, OUT debits; no separate ordinary payment for new Exchange Sale. A single Exchange cannot be charged/refunded twice for the same settlement key.

## Security, financial precision, recovery
- Uses AuthProvider effective permissions, not role names. Permissions are independent: PAYMENTS_CREATE≠PAYMENTS_READ, EXPENSES_CREATE≠FINANCE_READ, EXCHANGES_SETTLE≠EXCHANGES_READ. Protected reads only enabled with actual grants; backend is the final authority.
- Amount inputs are **decimal integer strings**, max 17 digits (existing backend @Digits where present). Money formatter uses bigint cents for exact string values. Backend BigDecimal may be serialized to JSON number; amounts above JS safe precision cannot be shown exactly and are rejected from exact checks — no promise of arbitrary BigDecimal precision. No frontend float financial arithmetic or optimistic balance updates.
- Shared `GuardedPost` requires explicit confirmation, disables double submit, and writes a **user-scoped, operation-scoped sessionStorage marker before POST**, containing only operation UUID and minimal non-sensitive metadata. No credentials, customer details, human comments, reference values or full financial logs persisted. If marker can't be safely written, the POST is not sent.
- Network, 409 and 5xx uncertainty: locked after reload in same browser tab; no automatic POST retry. Exact in-memory payload replay only permitted for backend-idempotent Refund, Settlement, Expense and Transfer with original idempotencyKey/transferId. Payment create/cancel and opening balance **do not** use unsupported idempotency keys, and are never automatically re-posted or offered manual blind retry.
- Settlement reconciliation: server GET /api/exchanges/{id}/settlements includes idempotencyKey and amount/direction/method, allowing positive confirmation of the exact posted operation before unlocking. RefundResponse, ExpenseResponse and PaymentResponse do NOT expose their original idempotency keys; an unrelated matching amount is insufficient proof of success, so unknown outcomes remain locked until reconciliation/authorized administration or exact safe same-key retry where available. Transfers have no GET /api/finance/transfers/{id}.
- If GET query invalidation fails after a **successful server POST**, this is an interface refresh failure, never a financial posting failure or reason for re-posting.
- 401/403/409/400 handled with existing ApiClientError/UI. Closed-day protections cannot be circumvented by moving dates or calling Daily Closing correction endpoint. No F11 daily-close writes here.

## Cache invalidation
Targeted TanStack keys: finance/accounts, finance/cash-flow, finance/expenses+total; sale payments + active, refunds, F07 sales detail/list/kanban, F09 exchange/settlement detail; no global cache purge except existing AuthProvider logout flow. Backend always computes CASH/BANK and Cash Flow.

## Tests and limits
- Frontend lint, TypeScript, Vitest/RTL and production Vite build via existing `Frontend verification` workflow.
- Dedicated `.github/workflows/f10-finance-integration.yml` runs actual Spring Boot/PostgreSQL Testcontainers, including PaymentApi, PaymentRefundIntegrity, RefundApi/Concurrency, ExchangeSettlement/Workflow, FinanceApi/EndToEnd/Transfer/OpeningBalance/Query, FinancialDocumentClosing and DailyClosingBoundary tests on isolated test data.
- Docker Compose smoke separately checks PostgreSQL/backend/frontend startup; not a browser→backend→database E2E. Do not claim full browser financial E2E without running it.
- No bank/M-Bank API integration, multi-currency, manual ledger, profit accounting, periodic close unlock, retroactive corrections or global payments/exchanges/refunds lists. F11 owns daily closing.
